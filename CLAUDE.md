# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MCPokédex — an agentic chat (Gemini-style) that answers Pokémon questions as "Dexter". A FastAPI backend runs a [strands-harness](https://github.com/strands-agents/harness-sdk) agent connected to the [`mcp-pokemon-server`](https://github.com/ShimaCoding/mcp-pokemon-server) MCP server. Tools that declare an MCP Apps widget (`_meta.ui.resourceUri`) render inline in the chat: the frontend acts as the MCP Apps **host**.

LLM: Groq only, through LiteLLM. Anonymous requests use `gpt-oss-20b`; requests with a valid `X-API-Key` use `gpt-oss-120b` with fallback to `gpt-oss-20b` (strands `ModelRouter`).

## Running the App

```bash
uv sync                                         # deps pinned in uv.lock
uv run uvicorn backend.main:app --reload        # backend on :8000
cd frontend && npm run dev                      # Vite on :5173, proxies /api, /config, /health
uv run pytest                                   # backend tests
uv run python -m backend.evals.harness run --label X --url http://127.0.0.1:8765   # quality evals (live LLM)
uv run python -m backend.evals.harness compare base.json cand.json                 # exit 1 on regression
uv run python -m backend.evals.phoenix_experiment run --label X --url http://127.0.0.1:8765 [--judge]  # same evals as a Phoenix experiment
docker-compose up --build                       # production-like
```

`.env` needs `GROQ_API_KEY`. For a local MCP server set `MCP_SERVER_URL=http://localhost:8001/mcp`. Dependencies are locked: update with `uv lock --upgrade-package X`, never with open ranges.

## Architecture

- **`backend/providers.py`** — Groq model lists and `build_model()`, which returns a `ModelRouter` of `TracedLiteLLMModel`s. `TracedLiteLLMModel` reports each attempt (`llm_call`, `model_attempt`) to a per-request trace sink. Nothing in litellm is patched.
- **`backend/agent.py`** — `create_agent()` builds the harness with everything unsafe for a public site disabled (`builtin_tools=[]`, `builtin_plugins=[]`, `memory=False`, `background_tasks=False`). The agent exposes exactly `EXPECTED_TOOLS` (the MCP tools, nothing else); `backend/tests/test_agent.py` enforces it. The Dexter narration protocol is inline in `SYSTEM_PROMPT` (`skills=False`, no harness skill), and `create_agent` re-applies `SYSTEM_PROMPT` after the session restore because snapshots persist the system prompt. `NormalizePokemonNames` turns Pokémon-name tool arguments into PokeAPI slugs ("Mr. Mime" → `mr-mime`, `giratina` → `giratina-altered`); the MCP server only lowercases. Never enable long-term memory: it is shared across all visitors.
- **`backend/context.py`** — multi-turn context policy, run as a strands `ContextManager` strategy before every model call (`stash=False`, so no `retrieve_context`). Past turns keep user text and tool calls (name + input); tool results become a "call the tool again" stub, replies are cut to `PAST_REPLY_CHARS`, reasoning is dropped, and only the last `MAX_PAST_TURNS` turns are kept. Dropped turns leave a one-line index ("[Turnos anteriores resumidos: 1) gengar (get_pokedex_entry); …]", last `INDEX_MAX_ENTRIES`) at the head of the oldest kept user message, so the model can re-call the tool for them. The current turn is never touched, and the compacted history is what the snapshot persists. `next_turn()` keeps a turn counter in agent state (`agent_init.turn`, `metadata.turn` on the agent span).
- **`backend/sessions.py`** — `conversation_id` validation (`^[a-z0-9-]{8,64}$`, generated by the browser), a per-conversation `asyncio.Lock`, and TTL cleanup of `SESSIONS_DIR` (harness snapshots under `session/<id>`; `context/<id>` only for pre-#18 conversations).
- **`backend/telemetry.py`** — agent tracing with two independent backends behind one interface: Datadog LLM Observability (enabled by `DD_API_KEY`) and Arize Phoenix (enabled by `PHOENIX_COLLECTOR_ENDPOINT`, see `telemetry_phoenix.py`); both at once while the Datadog trial lasts. Helpers yield a `_Span(dd, px)`; `export_ids` hands the frontend Datadog's ids when it is on (Phoenix maps them to its own span), else Phoenix's (32-hex trace, decimal span, same `FeedbackRequest` contract). Datadog goes through the ddtrace SDK in agentless mode (no Datadog Agent, APM tracer off). Each request is an `agent` span (session = `conversation_id`, opened in `_sse_generator`) with an `llm` span per model call (`TracedLiteLLMModel.stream`: messages, output, tokens incl. cached) and a `tool` span per tool call (`_ToolTrace`). Spans carry `env` (`DD_ENV`, default `local`; `docker-compose.yml` pins `prod`) and `version` (the git commit from `backend/build_info.py`, also on `/health`; `DD_VERSION` overrides it, never set it in Dokploy). Without either backend every helper is a no-op, and telemetry never breaks a request. Strands' OTel export is not used: its OTLP spans reached Datadog APM but never LLM Observability, and for Phoenix it also exports HTTP/MCP/event-loop spans and puts token counts on its agent span.
- **`backend/telemetry_phoenix.py`** — Phoenix backend: OTel spans with OpenInference conventions (`openinference.span.kind` AGENT/LLM/TOOL, `session.id`, `llm.model_name`/`llm.provider`, `llm.token_count.*` incl. `prompt_details.cache_read`, `llm.input_messages`/`llm.output_messages` with structured tool calls, `llm.tools`; `env`/`version` and annotate's metadata/tags in `metadata`). Private `TracerProvider` (Strands/FastAPI spans on the global one must not reach Phoenix); the agent span is never attached to the OTel context (the SSE generator may close in another context), children find it through a ContextVar. Token counts only on llm spans: Phoenix sums them into the agent span's `cumulative_llm_token_count_*`. Evals and 👍/👎 are span annotations (`POST /v1/span_annotations?sync=false` from a one-thread worker; Phoenix queues them until the span lands). Project `PHOENIX_PROJECT_NAME`, default `mcpokedex-<env>`.
- **`backend/tool_cache.py`** — process-level cache (TTL 24 h, LRU 512) for `get_pokedex_entry`, plugged into every agent as `ExecuteToolStage` middleware. A hit skips the MCP server and PokeAPI and returns the same result dict (same widget `CallToolResult`); only complete results are stored, and an expired copy is served if the live call fails. `tool_result` carries `cached`/`duration_ms` and the tool span a `cache` tag. Env: `TOOL_CACHE_ENABLED`, `TOOL_CACHE_TTL_SECONDS`, `TOOL_CACHE_MAX_ENTRIES`.
- **`backend/evals/`** — quality evals. `checks.py` (no I/O): `pokemon_tool_used`, `dexter_persona`, `grounded_facts`; `_sse_generator` runs them after `done` and submits them as evaluations on the agent span (`telemetry.submit_evaluations`). `harness.py` is an SSE client that runs the labeled conversations in `cases.json` against any backend (`--repeat`, optional Groq judge from `judge.py`, `--submit` only to a local backend on a non-prod ml_app); `compare` is the quality gate for prompt/model/context changes: a drop fails only beyond its tolerance and z > 1.96 (two-proportion z-test), `completed`/`no_invented_entry` fail on any drop, and judge metrics are informational unless `--gate-judge`. Cases use tool *sets* and never expect `skills`. `phoenix_experiment.py` runs the same cases as a Phoenix experiment (dataset `mcpokedex-cases`, one example per case; task = the conversation via `harness.run_turn`; one evaluator per harness metric, score = pass share over the case's turns, `n/a` when it does not apply; `judge_persona` = judge mean) and also writes the harness JSON, so `harness compare` stays the gate. Phoenix = `--phoenix-url` or `PHOENIX_COLLECTOR_ENDPOINT` (+ `PHOENIX_API_KEY`); the dataset is never overwritten: changed cases need a new `--dataset` name. `arize-phoenix-client` is a dev dependency (not in the image).
- **`backend/feedback.py`** — 👍/👎: `done` carries `trace_id`/`span_id` when LLM Obs is on; `POST /api/feedback` accepts only spans this process issued (in-memory, one vote each) and calls `LLMObs.submit_feedback`.
- **`backend/mcp_gateway.py`** — short-lived MCP connections for non-agent endpoints: widget HTML (`read_ui_resource`) and widget tool calls (`call_ui_tool`), both restricted to UI-bound tools and cached for 5 min.
- **`frontend/`** — React + Vite chat (builds into `backend/static`). `hooks/useAgentStream.ts` streams a reply into the chat store as ordered text/widget parts plus traces; `components/Widget/WidgetFrame.tsx` is the MCP Apps host (sandboxed `srcdoc` iframe with CSP from `_meta.ui.csp`, `AppBridge` over postMessage, lazy-loaded); `components/Thinking/ThinkingPanel.tsx` is the "ver cómo lo pensó" trace panel. `conversation_id` and recent messages persist in localStorage; "Nueva" starts a new conversation.
- **`backend/main.py`** — FastAPI app. `POST /api/agent/run` streams SSE; `GET /api/ui-resource?uri=` and `POST /api/mcp/call-tool` back the widget bridge. Static frontend mounted at `/`.
- **`observability/phoenix/docker-compose.yml`** — Phoenix 21 (pinned) + its own `postgres:16-alpine`, a raw compose app in Dokploy; secrets only in the Dokploy env. Public at `phoenix.shimadev.xyz` with auth on (UI, REST, and OTLP `/v1/traces`, which needs an API key); the agent sends OTLP over `dokploy-network` to `http://mcpokedex-phoenix:6006` with its system key, eval experiments from dev machines use a separate system key (`mcpokedex-evals`) and the public route. Retention 60 days (`PHOENIX_DEFAULT_RETENTION_POLICY_DAYS`). The `mcpokedex-prod` project has categorical annotation configs (set through the Phoenix API, not in this repo): `user_feedback` thumbs_up=1/thumbs_down=0 and the rule evals `pokemon_tool_used`/`dexter_persona`/`grounded_facts` pass=1/fail=0, all maximize; new annotation names need a config too.
- **`observability/grafana/`** — provisioning for the existing Grafana (`/root/monitoring` on the VPS, not Dokploy): read-only Postgres datasource `phoenix-pg` (role `grafana_ro` from `grafana-ro.sql`, SELECT on the trace tables only: the DB also holds users, API keys and secrets), the dashboard "MCPokedex Agent — Phoenix" and `alert-rules-mcpokedex.yml`, the same three monitors as Datadog in SQL over root AGENT spans of `mcpokedex-prod` (`100 * bad / greatest(count, 20) > 5` over 1 h), notified through the default policy (`telegram-shima`). `backend/tests/test_grafana_alerts.py` pins them.
- **`observability/datadog/monitors.json`** — the three Datadog monitors (agent latency p95 > 5 s, error % > 5%, tokens/query p95 > 15k) as `llm-observability alert` formulas `bad / clamp_min(all, 20) * 100 > 5` over 1 h on agent spans; `backend/tests/test_monitors.py` pins them to the code. No `@` handles in the file. Error spans: a failure before the agent runs (MCP connect, session restore) gets an error agent span tagged `failure_stage:setup` (`telemetry.record_failed_request`); a browser disconnect is not an error (`client_disconnected:true`).

## SSE contract

Each event is `data: <json>\n\n`; `type` is one of `start`, `agent_init`, `llm_call`, `model_attempt`, `tool_call`, `tool_result`, `ui_resource`, `text`, `done`, `error` (full shapes in the `_sse_generator` docstring). `tool_call`/`tool_result`/`ui_resource` share `tool_id` and `index`. `ui_resource` carries `resource_uri`, `tool_input` and `tool_result` (MCP `CallToolResult` shape with `structuredContent`) — everything the frontend needs to mount the widget. `timestamp_ms` is when the event happened (ms since request start); trace events are delivered between model stream events, so they can reach the client later than their stamp, while each `text` delta goes out as its own chunk (`backend/tests/test_streaming.py`). New event types must also be added to `EVENTS_CATALOG` in `backend/wiki_content.py` (a test checks it).

## Key Design Decisions

- **Agent per request**: the harness agent (and its MCP connection) is built per request in a worker thread and cleaned up afterwards; conversation memory lives in the session snapshot, not in the process.
- **Widgets never talk to MCP directly**: the iframe is sandboxed (`allow-scripts` only) and the browser has no MCP client, so widget requests go through the backend endpoints above.
